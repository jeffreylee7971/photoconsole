## 1. System Classification

**System Type:** CV/ML Pipeline

**Description:**
PhotoConsole Phase 3 is a local-first CV/ML pipeline that groups visually similar photos in a personal library and ranks each group by image quality so the user can identify redundant shots and select a keeper to keep. A solo user (managing their own family photo archive) runs `photoconsole cluster` to detect near-duplicate and same-scene photo groups using a two-pass approach — perceptual hashing (pHash) for rapid near-identical detection, followed by CLIP semantic embeddings and DBSCAN clustering for broader visual similarity. The pipeline then scores each photo on sharpness, resolution, face count, and EXIF completeness, auto-proposes the highest-scoring photo as the keeper, and lets the user confirm or override via a Rich terminal review UI. The final output is a deletion manifest (CSV + .bat) listing redundant photos for the user to delete manually. "Good" means: burst shots from the same moment land in the same cluster, the sharpest photo in each cluster is auto-picked, photos from different events are never merged, and the whole pipeline completes on a 100K-item catalog within hours on a Ryzen 9 5900X (CPU path).

**Critical Failure Modes:**
1. **Cross-event cluster merge:** Photos from different family events (e.g., a birthday party and a beach trip both containing people in similar lighting) are placed in the same cluster. The user sees them grouped together, approves a deletion, and permanently removes photos from an unintended event.
2. **Wrong keeper selected:** The pipeline auto-picks a blurry or lower-resolution photo as the keeper while the sharpest version exists in the same cluster. If the user accepts the auto-pick without opening the photos for visual comparison, the blurry copy survives and the sharp copy is flagged for deletion.
3. **Burst-shot split (silent miss):** Near-identical rapid-fire shots from a single shutter burst are scattered across multiple clusters or excluded as noise. The user never sees them grouped, so they cannot efficiently pick one — the entire value proposition of the tool is lost for burst sequences.
4. **EXIF-poisoned quality score:** A photo without `date_taken` metadata is penalized 10% on the EXIF completeness signal. If a large proportion of photos are missing EXIF data (e.g., screenshots, scanned prints, cloud-downloaded copies), the quality ranking systematically elevates metadata-complete photos regardless of actual visual quality — the sharpest shot may rank below a softer shot that has GPS coordinates.
5. **Oversized cluster overwhelming review:** A long continuous event (a full-day trip, several hundred burst shots) produces a single cluster of 100+ photos. The terminal review UI becomes unusable and the user skips the cluster entirely, receiving no value from the run.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Personal Digital Photo Curation / Consumer Photo Library Management

**User Population:** Solo user managing a personal family photo archive (10K–100K items across local SSD, NAS, and cloud mirrors). Power user comfortable with CLI tools. Acts as both the photographer and the curator — there is no separate domain expert panel. The user's own visual judgment is the ground truth.

**Stakes Level:** Medium

**Output Consequence:** The pipeline produces a deletion manifest. The user reviews it and runs a `.bat` file to delete redundant photos. PhotoConsole never deletes — there is always a manual review gate. If the clustering or keeper selection is wrong, the user either notices during review (low stakes: manual rework) or misses it and deletes a photo they wanted to keep (medium stakes: permanent loss of an irreplaceable family memory if no backup exists). Because the user has a NAS backup, total loss is unlikely but not impossible for photos that exist only on one source.

### What Domain Experts Evaluate Against

The "domain expert" for this system is the user themselves. The following rubric dimensions are what a careful photographer/curator would judge when reviewing the pipeline's output — derived from practitioner knowledge of photo culling workflows, the IEEE research on automated photo albuming and quality screening, and production failure mode observations from large-scale image deduplication systems.

---

**Dimension:** Cluster scene coherence
**Good (user accepts):** All photos in a cluster were taken in the same scene or shoot context — same location, same subjects, close timestamps. Opening any two photos from the cluster in Windows Photos confirms they are clearly related shots.
**Bad (user flags):** A cluster contains photos from two different family events that happen to share visual similarity (e.g., all outdoor photos with similar sky color). The user must manually inspect every photo in the cluster to separate them.
**Stakes:** High
**Source:** IEEE research on automated event clustering of consumer photos (Zhao et al.); production deduplication systems report that images with dense repetitive features (similar backgrounds, uniform lighting) are the primary source of cross-event false-positive merges.

---

**Dimension:** Keeper pick accuracy
**Good (user accepts):** The auto-suggested keeper is visually the sharpest photo in the cluster when compared side-by-side in Windows Photos. Resolution ties are broken by the higher-resolution copy. If faces are present, the keeper shows clearly recognizable faces.
**Bad (user flags):** The auto-suggested keeper is noticeably softer or lower-resolution than another photo in the same cluster. The user overrides the auto-pick more than once per review session.
**Stakes:** High
**Source:** Consumer photo culling practice — sharpness is the primary criterion photographers use to select among burst shots (D-08: sharpness weighted 45%). A blurry keeper surviving while the sharp copy is deleted is the worst outcome short of cross-event merge.

---

**Dimension:** Burst sequence capture rate
**Good (user accepts):** Rapid-fire burst shots (same subject, taken within 1–3 seconds of each other, nearly pixel-identical) are grouped together in a single cluster or pHash near-duplicate group. The user can review the burst as a unit and pick one.
**Bad (user flags):** Burst shots appear as isolated noise (cluster_id = NULL) or are split across two or more clusters. The user has to hunt for related shots manually, defeating the purpose of the tool.
**Stakes:** High
**Source:** Practitioner knowledge — burst mode is the dominant source of redundant photos in modern smartphone libraries. The pHash Hamming ≤ 10 threshold is specifically calibrated for this use case; failure here is the most common complaint with photo-dedup tools.

---

**Dimension:** Review workload per run
**Good (user accepts):** The number of clusters surfaced per run is manageable in one sitting — roughly 10–50 clusters for a typical incremental scan, each with 2–10 photos. Cluster size distribution is right-skewed: many small clusters, few large ones.
**Bad (user flags):** A single cluster contains 50+ photos (an entire multi-hour event). The terminal review UI cannot meaningfully display it. The user skips it. Alternatively, hundreds of clusters with 2–3 photos each make the session feel like triaging noise.
**Stakes:** Medium
**Source:** UX research on photo management tools (pics.io, Excire Foto user feedback 2024–2025) — users abandon AI-assisted culling workflows when the review task feels larger than manual inspection. Cluster size caps and noise filtering are the primary levers.

---

**Dimension:** Quality score transparency
**Good (user accepts):** The review table shows individual component scores (sharpness, resolution, face count, EXIF bonus) alongside the combined score for each photo. The user can see why one photo ranked above another without opening both files.
**Bad (user flags):** Only the combined 0–100 score is shown. The user cannot tell if a photo ranked highly because it is sharp or because it has GPS metadata. When the auto-pick seems wrong, there is no way to diagnose why.
**Stakes:** Medium
**Source:** D-11 (CONTEXT.md) — showing component scores is an explicit design requirement; opacity in quality ranking erodes trust in the auto-pick, causing users to override every suggestion rather than reviewing selectively.

### Known Failure Modes in This Domain

1. **Visual-similarity hub images:** Photos with dense, uniform backgrounds (clear blue sky, sand, solid-color walls) produce CLIP embeddings that are geometrically close to many other photos regardless of subject. These "hub" images can bridge otherwise unrelated clusters, causing a chain of false-positive merges. Production image deduplication research (Princeton CASS group, DZone scaling article) identifies hub images as the primary cause of runaway cluster growth.

2. **EXIF date absence skewing quality ranks:** Photos migrated from cloud services (Google Photos, iCloud exports), scanned prints, or screenshots frequently lack `date_taken` and GPS metadata. The 10% EXIF completeness penalty unfairly ranks these photos lower, even if they are the sharpest copy. On libraries with large cloud-migrated sets, this systematically inverts the keeper selection for entire date ranges.

3. **Solid-color / black / white image embedding collapse:** Photos that are nearly solid-color (underexposed blacks, overexposed whites, blank frames from camera errors) produce near-zero CLIP embeddings that cluster together regardless of actual content. This creates spurious clusters of "bad photos" that may also pull in legitimately dark or high-key intentional shots.

4. **Threshold sensitivity across different shooting conditions:** A single global DBSCAN eps threshold (0.25 cosine distance) that works well for burst shots in consistent lighting may over-merge photos from a slow walk through different rooms of a house, or under-merge shots from a fast-action sequence with motion blur variation. The user has no feedback mechanism to know the threshold is misconfigured until they review clusters and find anomalies.

## 2. Framework Decision

**Selected Framework:** OpenCLIP (open-clip-torch) + scikit-learn + OpenCV + imagehash

**Version:** open-clip-torch==2.24.0, scikit-learn>=1.4, opencv-python-headless>=4.9, imagehash>=4.3.1, torch (CPU default; ROCm 6.3 wheel for Linux GPU)

**Rationale:**
Phase 3 is a local CV/ML pipeline — not an LLM orchestration task. The selected stack is the only coherent fit: imagehash delivers fast pHash pre-filtering (Hamming distance ≤ 10 for near-identical detection), OpenCLIP provides ROCm-compatible CLIP embeddings (ViT-B-32, laion2b weights) that fit comfortably within the RX 6750 XT's 12GB VRAM, scikit-learn's DBSCAN handles density-based clustering without requiring a pre-specified cluster count, and OpenCV supplies Laplacian variance for blur scoring and Haar cascades for face counting. The entire stack is open-source, runs fully offline (satisfies NFR2 privacy), and integrates cleanly into the existing Python 3.12 + SQLAlchemy + Click project.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| sentence-transformers + faiss | Viable fallback if open-clip-torch ROCm wheel unavailable on Windows; slightly less control over exact ViT-B-32 weights |
| LangChain / LlamaIndex / CrewAI / LangGraph | LLM orchestration frameworks — not applicable to a CV/ML pipeline with no language model |
| CUDA-only builds (torchvision, clip-openai) | User hardware is AMD RX 6750 XT (ROCm, not CUDA) — CUDA builds will not use the GPU |

**Vendor Lock-In Accepted:** No — all libraries are open-source (MIT/Apache 2); model weights downloadable from OpenCLIP hub without account

### Entry Point Pattern

```python
"""
Minimal copy-paste runnable: two-pass pHash -> CLIP -> DBSCAN pipeline.
Assumes image paths come from the catalog; embeddings are returned as numpy arrays
for downstream SQLite BLOB storage.
"""
from __future__ import annotations

import struct
from pathlib import Path

import imagehash
import numpy as np
import open_clip
import torch
from PIL import Image
from sklearn.cluster import DBSCAN
from sklearn.metrics.pairwise import cosine_distances

# ---------------------------------------------------------------------------
# 1. Device selection — CPU default on Windows AMD; GPU on Linux ROCm
# ---------------------------------------------------------------------------

def select_device() -> torch.device:
    """Return the best available device. On Windows with AMD, this is always CPU."""
    if torch.cuda.is_available():
        return torch.device("cuda")
    # ROCm exposes through cuda API on Linux; no detection path on Windows
    return torch.device("cpu")

DEVICE = select_device()

# ---------------------------------------------------------------------------
# 2. Load CLIP model once — expensive; do this at module/process startup
# ---------------------------------------------------------------------------

def load_clip_model():
    model, _, preprocess = open_clip.create_model_and_transforms(
        "ViT-B-32",
        pretrained="laion2b_s34b_b79k",
    )
    model = model.to(DEVICE)
    model.eval()
    return model, preprocess

# ---------------------------------------------------------------------------
# 3. Pass 1: pHash pre-filter — group near-identical images (Hamming <= 10)
# ---------------------------------------------------------------------------

def compute_phash(path: Path) -> imagehash.ImageHash:
    with Image.open(path) as img:
        return imagehash.phash(img)

def are_near_identical(h1: imagehash.ImageHash, h2: imagehash.ImageHash, threshold: int = 10) -> bool:
    return (h1 - h2) <= threshold

# ---------------------------------------------------------------------------
# 4. Pass 2: CLIP embeddings — batch encode images, L2-normalise
# ---------------------------------------------------------------------------

_BATCH_SIZE = 50  # matches existing project pattern

def embed_images(
    paths: list[Path],
    model,
    preprocess,
    batch_size: int = _BATCH_SIZE,
) -> np.ndarray:
    """Return L2-normalised embeddings, shape (N, 512), dtype float32."""
    all_embeddings: list[np.ndarray] = []

    for i in range(0, len(paths), batch_size):
        batch_paths = paths[i : i + batch_size]
        images = []
        for p in batch_paths:
            try:
                img = preprocess(Image.open(p).convert("RGB"))
                images.append(img)
            except Exception:
                # Corrupt / unreadable image — insert zero vector; caller handles
                images.append(torch.zeros(3, 224, 224))

        batch_tensor = torch.stack(images).to(DEVICE)
        with torch.no_grad():
            features = model.encode_image(batch_tensor)
            features = features / features.norm(dim=-1, keepdim=True)  # L2 normalise
        all_embeddings.append(features.cpu().numpy().astype(np.float32))

    return np.vstack(all_embeddings)

# ---------------------------------------------------------------------------
# 5. DBSCAN clustering on cosine distance matrix
# ---------------------------------------------------------------------------

def cluster_embeddings(
    embeddings: np.ndarray,
    eps: float = 0.25,   # cosine distance threshold; tune via knee-point analysis
    min_samples: int = 2,
) -> np.ndarray:
    """Return cluster label array; -1 = noise (no similar neighbours)."""
    # cosine_distances returns values in [0, 2]; 0 = identical, 2 = opposite
    dist_matrix = cosine_distances(embeddings)
    labels = DBSCAN(
        eps=eps,
        min_samples=min_samples,
        metric="precomputed",
        n_jobs=-1,
    ).fit_predict(dist_matrix)
    return labels

# ---------------------------------------------------------------------------
# 6. Embedding serialisation — SQLite BLOB (float32 little-endian)
# ---------------------------------------------------------------------------

def embedding_to_blob(embedding: np.ndarray) -> bytes:
    """Pack a float32 embedding vector as raw bytes for SQLite BLOB storage."""
    return embedding.astype(np.float32).tobytes()

def blob_to_embedding(blob: bytes) -> np.ndarray:
    """Unpack a SQLite BLOB back to a float32 numpy array."""
    n = len(blob) // 4  # 4 bytes per float32
    return np.frombuffer(blob, dtype=np.float32).copy()
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `open_clip.create_model_and_transforms()` | Loads the ViT-B-32 model + image preprocessing pipeline. Returns `(model, _, preprocess)` — the second return value is a text transform, unused here. | Once at startup; keep the model in memory for the entire cluster run. |
| `model.encode_image(batch_tensor)` | Runs the vision transformer on a batch of preprocessed image tensors; returns raw embeddings (not yet normalised). | Inside the batch loop; always L2-normalise immediately after. |
| `DBSCAN(metric="precomputed")` | Density-based clustering that accepts a precomputed distance matrix instead of raw features. Avoids recomputing distances inside the algorithm. | After computing `cosine_distances(embeddings)` — pass the distance matrix directly. |
| `imagehash.phash` / `hash1 - hash2` | Perceptual hash that survives JPEG recompression and minor resizing. The `-` operator returns Hamming distance as an integer. | Pass 1 pre-filter; skip CLIP for any pair with Hamming ≤ 10. |
| `cv2.Laplacian(gray, cv2.CV_64F).var()` | Computes the variance of the Laplacian operator on a greyscale image; higher = sharper. Zero-cost signal: no model required. | Inside `quality.py` to populate `blur_score` on each `MediaFile`. |

### Common Pitfalls

1. **Passing cosine similarity (not distance) to DBSCAN.** `cosine_similarity()` returns values in [-1, 1] where 1 = identical. DBSCAN interprets `eps` as a maximum *distance*, so passing a similarity matrix inverts the logic entirely — similar images end up with "large distance" and never cluster. Always use `cosine_distances()` (= 1 - cosine_similarity) or `1 - cosine_similarity(X)` explicitly. ([sklearn docs](https://scikit-learn.org/stable/modules/generated/sklearn.cluster.DBSCAN.html))

2. **Loading the CLIP model inside a loop or worker thread.** `open_clip.create_model_and_transforms()` downloads weights (~350 MB for ViT-B-32) on first call and is slow (~2–5s even from cache). Loading it per-batch or per-worker causes extreme slowdown. Load once in the main process before the ThreadPoolExecutor is created and pass the model reference to workers.

3. **Forgetting `.convert("RGB")` before preprocessing.** PIL opens JPEG as RGB but PNG as RGBA and some TIFFs as palette-mode. OpenCLIP's preprocess pipeline (`transforms.Normalize`) expects a 3-channel tensor; passing a 4-channel RGBA image will raise a shape mismatch at `model.encode_image`. Always call `.convert("RGB")` before `preprocess()`.

4. **Using `DBSCAN` with `eps` tuned on Euclidean space when cosine distance is used.** The default `eps=0.5` in sklearn is calibrated for Euclidean data. Cosine distances of L2-normalised CLIP embeddings for visually similar photos typically fall in the 0.10–0.30 range. Starting at `eps=0.5` will merge unrelated clusters. Use a k-nearest-neighbour distance plot (sorted distances to the k-th neighbour) to identify the knee point — typically 0.20–0.30 for ViT-B-32 photo embeddings.

5. **pHash Hamming distance breaks across imagehash major versions.** Version 4.0 changed the binary-to-hex representation, meaning hashes stored by version 3.x are not comparable with version 4.x hashes. If the catalog ever contains hashes computed by an earlier install, clustering will produce nonsense. Pin `imagehash>=4.3.1` in `requirements.txt` and document the version in the schema migration notes. If hashes were stored previously, re-compute them.

## 4. Implementation Guidance

**Model Configuration:**

- **CLIP model:** `ViT-B-32` with pretrained weights `laion2b_s34b_b79k` (66.6% ImageNet top-1 zero-shot; ~350 MB download). The embedding dimension is 512 floats — compact enough for 100K-item cosine distance matrices (~20 GB float32 dense; use sparse NearestNeighbors approach above 50K items).
- **Batch size:** 50 images per forward pass — matches `_BATCH_SIZE = 50` established in `cli.py`. On CPU this keeps memory flat; adjust up to 128 on GPU if VRAM allows.
- **Device:** CPU is the practical default on Windows with AMD RX 6750 XT. ViT-B-32 on CPU (Ryzen 9 5900X, 12 threads) processes approximately 8–15 images/second. At that rate, 10K images takes ~12 minutes — acceptable for a one-time or incremental run. On Linux with ROCm 6.3 on the same card, throughput increases to ~80–120 images/second.
- **pHash threshold:** Hamming ≤ 10 (out of 64 bits for default hashsize=8). Catches JPEG recompression, 10–30% resize, minor rotation. Below 6 is near-pixel-identical; above 14 starts capturing different subjects in similar lighting.
- **DBSCAN eps:** Start at 0.25 cosine distance. Tune using the k-NN knee-point method on a sample of 1000 embeddings. Values in the 0.20–0.35 range are typical for photo clusters; go lower (0.15) if false merges appear, higher (0.35) if related shots are split.
- **Quality weights:** Defaults from `config.yaml` — sharpness 0.45, resolution 0.30, faces 0.15, EXIF completeness 0.10. All configurable without code changes.

**Core Pattern:**

```python
# photoconsole/clustering.py — _run_cluster() pure helper (no click dependency)
from __future__ import annotations

import logging
from pathlib import Path
from typing import Iterator

import numpy as np
from sqlalchemy.orm import Session

from photoconsole.catalog.db import session_factory
from photoconsole.catalog.models import MediaFile
from photoconsole.clustering import (
    load_clip_model,
    embed_images,
    cluster_embeddings,
    embedding_to_blob,
    blob_to_embedding,
)
from photoconsole.quality import compute_quality_scores

logger = logging.getLogger(__name__)
_BATCH_SIZE = 50


def _run_cluster(
    catalog_path: str,
    eps: float = 0.25,
    min_samples: int = 2,
    phash_threshold: int = 10,
    quality_weights: dict | None = None,
) -> dict:
    """
    Pure helper: run the two-pass clustering pipeline.
    Returns a summary dict for the click wrapper to display.
    Single writer thread: all DB writes happen here (main thread).
    """
    engine = create_catalog_engine(catalog_path)
    Session = session_factory(engine)

    # --- Pass 0: compute quality scores for any files missing them ---
    with Session() as session:
        unscored = session.query(MediaFile).filter(MediaFile.blur_score.is_(None)).all()
    if unscored:
        logger.info("Computing quality scores for %d files", len(unscored))
        scored_results = compute_quality_scores(
            [Path(f.path) for f in unscored],
            weights=quality_weights or {},
        )
        with Session() as session:
            for mf, scores in zip(unscored, scored_results):
                mf.blur_score = scores["blur_score"]
                mf.pixel_width = scores["pixel_width"]
                mf.pixel_height = scores["pixel_height"]
                mf.face_count = scores["face_count"]
            session.commit()

    # --- Pass 1: pHash pre-filter — mark near-identical pairs ---
    # (pHash pre-filter groups are handled at review time; not written to cluster_id)

    # --- Pass 2: load embeddings; embed missing files ---
    model, preprocess = load_clip_model()

    with Session() as session:
        all_files = session.query(MediaFile).filter(MediaFile.path.isnot(None)).all()
        missing_embed = [f for f in all_files if f.embedding_blob is None]

    if missing_embed:
        logger.info("Embedding %d new files", len(missing_embed))
        paths = [Path(f.path) for f in missing_embed]
        embeddings = embed_images(paths, model, preprocess, batch_size=_BATCH_SIZE)
        with Session() as session:
            for mf, emb in zip(missing_embed, embeddings):
                mf.embedding_blob = embedding_to_blob(emb)
            session.commit()

    # --- Pass 3: cluster all embeddings ---
    with Session() as session:
        files_with_embed = (
            session.query(MediaFile)
            .filter(MediaFile.embedding_blob.isnot(None))
            .all()
        )
        ids = [f.id for f in files_with_embed]
        blobs = [f.embedding_blob for f in files_with_embed]

    if len(ids) < 2:
        return {"clusters": 0, "clustered_files": 0, "noise": len(ids)}

    embeddings_matrix = np.vstack([blob_to_embedding(b) for b in blobs])
    labels = cluster_embeddings(embeddings_matrix, eps=eps, min_samples=min_samples)

    # --- Write cluster_id assignments (main thread, single writer) ---
    with Session() as session:
        for file_id, label in zip(ids, labels):
            mf = session.get(MediaFile, file_id)
            mf.cluster_id = int(label) if label != -1 else None
        session.commit()

    n_clusters = len(set(labels)) - (1 if -1 in labels else 0)
    n_noise = int((labels == -1).sum())
    return {
        "clusters": n_clusters,
        "clustered_files": int((labels != -1).sum()),
        "noise": n_noise,
    }
```

**Tool Use / Integrations:**

- **OpenCV Haar cascade:** The `haarcascade_frontalface_default.xml` file ships with `opencv-python-headless` at `cv2.data.haarcascades + "haarcascade_frontalface_default.xml"`. Do not hardcode the path — use this attribute so it works on any install.
- **Laplacian blur:** `cv2.imread()` returns BGR by default. Convert to greyscale with `cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)` before `cv2.Laplacian(gray, cv2.CV_64F).var()`. Never call `.var()` on the BGR image — the result will be inflated and meaningless as a sharpness metric.
- **PIL vs cv2 for image loading:** OpenCLIP uses PIL; OpenCV uses its own loader. To avoid double-loading, use PIL for embedding and cv2 only for quality scores. Keep quality computation in a separate `quality.py` pass so the two loading paths do not interact.
- **Rich progress:** Use `rich.progress.track(iterable, description="...")` for batch loops. Do not mix `tqdm` (used in existing phases) with `rich.progress` in the same output — choose one. Phase 3 is green-field, so use Rich consistently with the review UI.

**State Management:**

- **Embeddings:** Stored as a `LargeBinary` column (`embedding_blob`) on `MediaFile`, serialised as little-endian float32 bytes (`embedding.tobytes()`). Deserialise with `np.frombuffer(blob, dtype=np.float32)`. A ViT-B-32 embedding is 512 * 4 = 2048 bytes per row — negligible SQLite overhead even at 100K files (200 MB total).
- **Incremental skip:** Before each embedding pass, query `MediaFile` where `embedding_blob IS NULL`. Only process those rows. This is the same `should_skip()` pattern already in `db.py` — extend it rather than reinvent it.
- **Quality scores:** Same incremental pattern — query `WHERE blur_score IS NULL`. Run quality computation on those files, write results in batches of 50 via `session.commit()`.
- **Cluster assignments:** Written as `cluster_id` (Integer, nullable) on `MediaFile`. `NULL` means either not clustered yet or genuinely no similar neighbours. A separate `cluster_run_id` column is not needed for Phase 3; a full re-cluster overwrites all assignments.
- **Single writer thread:** The main thread owns all `session.commit()` calls. Worker threads (ThreadPoolExecutor) compute quality scores and return result dicts — they never touch the session. This matches the pattern in `cli.py` (T-02-02).

**Context Window Strategy (adapted for CV/ML pipeline):**

This pipeline has no LLM context window. The analogous concern is **memory footprint as catalog size scales:**

- At 10K files: 512-dim float32 cosine distance matrix = 10K × 10K × 4 bytes = ~400 MB RAM — feasible on 64 GB.
- At 100K files: 100K × 100K × 4 bytes = ~40 GB RAM — exceeds available memory. Switch to a sparse neighborhood graph before reaching this scale.
- **Sparse fallback (implement before 50K items):** Use `sklearn.neighbors.NearestNeighbors(radius=eps, algorithm="ball_tree", metric="cosine")` to compute only the within-eps neighbors, then pass the sparse graph as `metric="precomputed"` to DBSCAN. This reduces memory from O(n²) to O(n * k) where k is the average cluster size.

### 4b.1 Structured Outputs with Pydantic (Config Validation for CV/ML Pipeline)

In a CV/ML pipeline, Pydantic is not used for LLM output parsing — it is used for **configuration validation**. The `ClusterConfig` and `QualityWeightsConfig` dataclasses in `config.py` carry the same validation burden that Pydantic `response_format` carries in LLM pipelines: catching misconfigured thresholds before they silently produce wrong results.

Use Pydantic (v2) for the new config sections instead of plain Python dataclasses to get field-level validation with clear error messages:

```python
# photoconsole/config.py — extend with Pydantic v2 models for Phase 3 config
from pydantic import BaseModel, Field, field_validator, model_validator
from typing import Annotated


class QualityWeightsConfig(BaseModel):
    """Weights for the four quality signals. Must sum to 1.0 (within float tolerance)."""

    sharpness: Annotated[float, Field(ge=0.0, le=1.0)] = 0.45
    resolution: Annotated[float, Field(ge=0.0, le=1.0)] = 0.30
    faces: Annotated[float, Field(ge=0.0, le=1.0)] = 0.15
    exif_completeness: Annotated[float, Field(ge=0.0, le=1.0)] = 0.10

    @model_validator(mode="after")
    def weights_sum_to_one(self) -> "QualityWeightsConfig":
        total = self.sharpness + self.resolution + self.faces + self.exif_completeness
        if abs(total - 1.0) > 1e-6:
            raise ValueError(
                f"quality_weights must sum to 1.0, got {total:.6f}. "
                f"Adjust sharpness/resolution/faces/exif_completeness in config.yaml."
            )
        return self


class ClusterConfig(BaseModel):
    """DBSCAN + pHash configuration for the cluster command."""

    eps: Annotated[float, Field(gt=0.0, lt=2.0, description="Cosine distance epsilon for DBSCAN")] = 0.25
    min_samples: Annotated[int, Field(ge=2, le=20)] = 2
    phash_threshold: Annotated[int, Field(ge=0, le=64)] = 10
    batch_size: Annotated[int, Field(ge=1, le=512)] = 50

    @field_validator("eps")
    @classmethod
    def eps_range_note(cls, v: float) -> float:
        if v > 0.5:
            # Not an error, but user likely misconfigured — cosine distance for
            # L2-normalised CLIP embeddings rarely exceeds 0.4 for related photos
            import warnings
            warnings.warn(
                f"cluster.eps={v} is unusually high for cosine distance. "
                "Values above 0.5 may merge unrelated clusters. "
                "Typical range: 0.15–0.35.",
                UserWarning,
                stacklevel=2,
            )
        return v


# Usage in load_config():
# cluster_section = raw.get("cluster", {}) or {}
# cluster_config = ClusterConfig(**cluster_section)          # raises on invalid input
# weights_section = raw.get("quality_weights", {}) or {}
# quality_weights = QualityWeightsConfig(**weights_section)  # raises if weights != 1.0
```

### 4b.2 Batch Processing Patterns (Replaces Async-First for CV/ML)

This pipeline is CPU/GPU-bound, not I/O-bound, so the relevant design concern is **batch efficiency** rather than async concurrency:

- **Quality score computation** (cv2 Laplacian, Haar cascade) is per-file and CPU-bound. Use `ThreadPoolExecutor` with `max_workers = os.cpu_count()` — the same pattern as `photoconsole/hasher.py:process_files`. Worker threads return result dicts; main thread writes to DB in batches of 50.
- **CLIP embedding** is GPU/CPU batch-bound. The model forward pass amortises overhead across the batch — do not call `model.encode_image()` one image at a time. A single-image "batch" is 5–10x slower per image than a batch of 50 due to fixed kernel launch overhead on both CPU and GPU.
- **The common mistake:** Calling `session.commit()` inside the worker thread alongside DB reads. SQLAlchemy's session is not thread-safe. Keep all session operations on the main thread; pass only result dicts between threads.
- **Incremental skip guard:** Check `embedding_blob IS NOT NULL` before the batch loop, not inside it. Building the "missing files" list once at the start avoids per-file DB roundtrips in the hot path.

```python
# Correct: worker returns a dict, main thread writes
def _compute_quality(path: Path) -> dict:
    """Thread-safe: no DB access, returns plain dict."""
    img_bgr = cv2.imread(str(path))
    if img_bgr is None:
        return {"path": str(path), "error": "unreadable"}
    gray = cv2.cvtColor(img_bgr, cv2.COLOR_BGR2GRAY)
    blur_score = float(cv2.Laplacian(gray, cv2.CV_64F).var())
    h, w = img_bgr.shape[:2]

    cascade_path = cv2.data.haarcascades + "haarcascade_frontalface_default.xml"
    cascade = cv2.CascadeClassifier(cascade_path)
    faces = cascade.detectMultiScale(gray, scaleFactor=1.1, minNeighbors=5, minSize=(30, 30))
    face_count = len(faces) if isinstance(faces, np.ndarray) else 0

    return {
        "path": str(path),
        "blur_score": blur_score,
        "pixel_width": w,
        "pixel_height": h,
        "face_count": face_count,
    }
```

### 4b.3 Prompt Engineering Discipline (Adapted: Threshold Discipline for CV/ML)

There are no LLM prompts in this pipeline. The equivalent discipline is **threshold documentation** — every numeric threshold must be explicitly chosen, justified, and exposed in config:

- **pHash threshold (10):** Document the choice. Hamming ≤ 6 catches near-pixel-identical images only; ≤ 10 catches JPEG recompression and ~20% resize; ≤ 16 starts catching different exposures of the same scene. The threshold is in `config.yaml` under `cluster.phash_threshold`.
- **DBSCAN eps (0.25):** Document the tuning method. The k-NN knee-point plot on a 1000-sample subset is the correct approach — not trial-and-error on full data. The threshold is in `config.yaml` under `cluster.eps`.
- **Quality weights:** The 45/30/15/10 split is a deliberate choice — sharpness dominates because a blurry keeper is always worse than a sharp duplicate. Document this reasoning in a comment in `config.yaml`. Weights are validated by Pydantic to sum to 1.0.
- **Never hardcode thresholds in business logic.** Every threshold lives in `ClusterConfig` or `QualityWeightsConfig`, loaded from `config.yaml`. This makes A/B testing threshold changes a config diff, not a code change.

### 4b.4 Context Window Management (Adapted: Memory Budget for Large Catalogs)

The analogous concern for a CV/ML pipeline is **in-memory data budget** as the catalog grows:

| Catalog Size | Dense Distance Matrix | Action |
|---|---|---|
| ≤ 10K files | ~400 MB | Safe — use dense `cosine_distances()` directly |
| 10K–50K files | 400 MB–10 GB | Warning at startup; prompt user to confirm or use sparse mode |
| > 50K files | > 10 GB | Mandatory sparse NearestNeighbors path (see below) |

```python
# Sparse fallback for large catalogs — prevents OOM at 50K+ files
from sklearn.neighbors import NearestNeighbors
import scipy.sparse

def cluster_embeddings_sparse(
    embeddings: np.ndarray,
    eps: float = 0.25,
    min_samples: int = 2,
) -> np.ndarray:
    """Memory-safe clustering for > 50K embeddings using sparse neighbor graph."""
    nn = NearestNeighbors(
        radius=eps,
        algorithm="ball_tree",
        metric="cosine",
        n_jobs=-1,
    )
    nn.fit(embeddings)
    # Returns sparse distance matrix — only within-eps pairs stored
    sparse_dist = nn.radius_neighbors_graph(embeddings, mode="distance")
    labels = DBSCAN(
        eps=eps,
        min_samples=min_samples,
        metric="precomputed",
        n_jobs=-1,
    ).fit_predict(sparse_dist)
    return labels
```

**Implementation note:** Add a size check in `_run_cluster()` — if `len(ids) > 50_000`, automatically use `cluster_embeddings_sparse()`. Log a notice so the user knows why. The dense path remains the default below 50K for simplicity and speed.

### 4b.5 Cost and Latency Budget

This pipeline has no per-call API cost (fully local). The budget is **time and hardware utilization:**

| Operation | Per-File Time (CPU, Ryzen 9 5900X) | 10K Files | 100K Files |
|---|---|---|---|
| pHash computation | ~5 ms | ~50 s | ~8 min |
| CLIP embedding (CPU, batch 50) | ~80 ms | ~13 min | ~2.2 hours |
| CLIP embedding (GPU, ROCm Linux) | ~10 ms | ~100 s | ~17 min |
| Laplacian blur (cv2) | ~2 ms | ~20 s | ~3 min |
| Haar cascade face detect | ~30 ms | ~5 min | ~50 min |
| DBSCAN (dense, 10K) | O(n²) ~2 s | 2 s | N/A (use sparse) |
| DBSCAN (sparse, 100K) | O(n·k) | N/A | ~30 s |

**Caching strategy:**
- Embeddings are the dominant cost. The incremental skip (`embedding_blob IS NOT NULL`) means a full re-embed only happens once per lifetime of the catalog. Subsequent runs only embed newly added files.
- Quality scores (blur, face count) are also incremental — computed once per file.
- **Never recompute embeddings for unchanged files.** If a file's `mtime` changes (edited, re-exported), its `embedding_blob` should be nullified so it re-embeds on the next run. Add a trigger or check in the scan phase that sets `embedding_blob = NULL` when `mtime` differs from the stored value.

**GPU acceleration path:**
- Windows with RX 6750 XT: CPU only (RDNA 2 not supported in Windows native ROCm as of 2026). Accept the ~2.2 hour estimate for 100K files as a one-time cost.
- Linux with RX 6750 XT + ROCm 6.3: install `torch` from the ROCm 6.3 wheel index. The unofficial `HSA_OVERRIDE_GFX_VERSION=10.3.0` env var may allow RDNA 2 to present as a supported target — community reports suggest it works for inference workloads but is not officially supported by AMD. Use at own risk; document clearly in the README if adopted.
- If GPU acceleration becomes a hard requirement on Windows, evaluate the `sentence-transformers` alternative with ONNX Runtime DirectML backend, which supports AMD GPUs on Windows without ROCm.

## 5. Evaluation Strategy

> Privacy constraint: all evaluation is local and code-based. No personal photos are sent to any external API or cloud service. LLM judges are not applicable to this system. The user is the sole human reviewer for qualitative assessment.
>
> Tooling constraint: Arize Phoenix (the GSD default for tracing) requires a running server process, which adds unnecessary complexity for a solo CLI tool. The simpler alternative — Python's `logging` module writing structured JSON to a SQLite metrics table — is used instead. See Section 7 for the monitoring schema.

### Dimensions

| Dimension | Rubric | Measurement | Priority |
|-----------|--------|-------------|----------|
| **Cluster scene coherence** | PASS: Every photo in a reference cluster shares the same labeled event (ground truth: user-labeled JSON). Cluster purity >= 0.90 across the reference dataset. FAIL: Any cluster contains photos from two different labeled events; purity drops below 0.85. | Code — cluster purity metric against manually labeled ground truth | Critical |
| **Keeper pick accuracy** | PASS: The file with the highest `quality_score` in a cluster matches the user-labeled keeper in >= 80% of reference clusters. FAIL: The auto-pick does not match the user-labeled keeper in > 20% of clusters, indicating the scoring formula is systematically mis-weighted. | Code — compare `argmax(quality_score)` per cluster against labeled keeper | Critical |
| **Burst sequence capture rate** | PASS: >= 90% of manually labeled burst groups (photos taken within 3 seconds, same subject) are assigned the same `cluster_id` or pHash group. FAIL: A labeled burst group is split across two or more cluster_ids, or any member has `cluster_id = NULL` (noise). Recall < 0.85 is a failure. | Code — recall on labeled burst groups: `|correctly grouped burst shots| / |total burst shots|` | Critical |
| **Review workload distribution** | PASS: >= 90% of clusters in a reference run contain <= 20 photos. No single cluster exceeds 50 photos. FAIL: Any cluster contains > 50 photos, OR > 10% of clusters contain > 20 photos, indicating over-merging at the current eps threshold. | Code — cluster size histogram; assert `max(cluster_sizes) <= 50` and `percentile(cluster_sizes, 90) <= 20` | High |
| **Quality score transparency** | PASS: The review table rendered by `photoconsole review-clusters` includes all four component columns (`sharpness`, `resolution`, `face_count`, `exif_bonus`) alongside the combined score. Each column is non-null for every row. FAIL: Any component column is missing from the Rich table output, or all rows show only the combined score. | Code — parse Rich table output in test; assert all four column headers are present | High |
| **Throughput at 100K items** | PASS: Full pipeline (quality scoring + embedding + DBSCAN) completes within 3 hours on CPU (Ryzen 9 5900X) for a 100K-item catalog. Incremental run (< 1K new files) completes within 5 minutes. FAIL: Full run exceeds 4 hours on CPU, or incremental run exceeds 15 minutes, making the tool impractical for regular use. | Code — timing benchmark with `time.perf_counter()`; compare against thresholds in `test_clustering.py::test_throughput_benchmark` | High |
| **EXIF-absent quality ranking** | PASS: On a test cluster where the sharpest photo (highest Laplacian variance) has no EXIF data, the quality score still ranks it within the top 2 photos of the cluster (i.e., the 10% EXIF penalty does not flip the ranking when blur differences are >= 20% apart). FAIL: A photo with 50% higher Laplacian variance than its cluster sibling ranks lower solely because of the EXIF completeness penalty — the sharpest copy is not the auto-pick. | Code — fixture test with a known-sharp/no-EXIF vs. known-soft/has-EXIF pair; assert rank order | High |
| **Embedding determinism** | PASS: Running `embed_images()` twice on the same input files (same model, same device) produces bit-identical output arrays. FAIL: Any embedding vector differs between runs (indicates non-deterministic model behavior or preprocessing randomness that would make incremental caching unreliable). | Code — `np.testing.assert_array_equal` on two runs of the same input batch | Medium |
| **Config validation gate** | PASS: `ClusterConfig` and `QualityWeightsConfig` raise `pydantic.ValidationError` on invalid input (e.g., `eps=5.0`, weights summing to 1.05) before any computation runs. FAIL: Invalid config values are silently accepted and used — the pipeline runs with a misconfigured threshold. | Code — parametrized pytest cases with invalid config inputs | Medium |
| **Hub image isolation** | PASS: A solid-blue-sky photo (known hub image type) with Laplacian variance < 10 does not appear in more than 2 distinct clusters when the reference dataset contains 5+ semantically unrelated clusters. FAIL: The hub image bridges 3+ unrelated clusters, indicating a false-positive merge chain. | Human review — inspect reference run output for known hub image paths | Medium |

## 6. Guardrails

> Context: this is a local CLI tool — there is no real-time inference pipeline to guard with latency budgets. "Online guardrails" here means preflight checks that run before the pipeline starts (catching configuration and dependency failures that would cause a crash mid-run) and per-cluster safety gates that skip gracefully rather than crashing. "Offline flywheel" means end-of-run signals that reveal threshold or scoring problems across runs.

### Pre-Run Preflight Checks (Online)

These run at the start of `photoconsole cluster` before any model loading or DB writes. A failed preflight exits immediately with a clear error message — no partial state is written.

| Guardrail | Trigger Condition | Intervention |
|-----------|------------------|--------------|
| **Dependency import check** | `import cv2` or `import open_clip` raises `ImportError` at startup | Exit with `SystemExit(1)` and print: "OpenCV / OpenCLIP not installed. Run: pip install open-clip-torch opencv-python-headless" |
| **CLIP model availability** | `open_clip.create_model_and_transforms("ViT-B-32", pretrained="laion2b_s34b_b79k")` raises or model cache directory does not exist | Exit with clear message: "CLIP model weights not found. First run will download ~350 MB from OpenCLIP hub. Ensure internet access on first run." |
| **Config validation** | `ClusterConfig` or `QualityWeightsConfig` raises `pydantic.ValidationError` on startup | Exit with full Pydantic error message showing which field failed and why. Never fall back silently. |
| **Catalog accessibility** | The catalog SQLite file does not exist or cannot be opened (permissions, corrupt) | Exit with: "Catalog not found at {path}. Run photoconsole scan first." |
| **Disk space for embeddings** | Available disk space on the catalog drive is < 500 MB (estimated: 100K × 2 KB embedding + 20% headroom) | Warn: "Low disk space ({available} MB free). Embedding storage may fail mid-run." Do not block — warn and continue. |
| **Memory budget warning** | `len(files_with_embedding) > 50_000` and dense distance matrix would exceed 10 GB | Warn user: "Catalog has {N} embedded files. Dense clustering requires ~{GB} GB RAM. Switching to sparse mode automatically." Switch to `cluster_embeddings_sparse()`. |

### Per-Cluster Safety Gates (Online)

These run during the pipeline and skip gracefully rather than crashing on individual file errors.

| Guardrail | Trigger Condition | Intervention |
|-----------|------------------|--------------|
| **Corrupt image skip** | `cv2.imread()` or `PIL.Image.open()` returns `None` or raises for a specific file | Log `WARNING: skipping corrupt/unreadable file: {path}`. Insert zero-vector embedding (marked as corrupt in DB). Exclude from clustering. Continue pipeline. |
| **Quality score failure skip** | `compute_quality_scores()` raises for a batch member (e.g., zero-byte file, unsupported format) | Log `WARNING: quality scoring failed for {path}: {error}`. Set `blur_score = NULL` for that file. Exclude from keeper ranking for its cluster. Do not crash. |
| **Oversized cluster gate** | A cluster produced by DBSCAN contains > 50 photos | Log `WARNING: cluster {id} contains {N} photos (exceeds 50-photo review limit). Consider lowering eps.` Flag the cluster in the DB with a `review_flag = "oversized"` attribute. Display the warning in the end-of-run summary table. |
| **Zero-variance embedding skip** | An embedding vector has L2 norm < 0.01 (near-zero — solid black/white image collapse) | Log `WARNING: near-zero embedding for {path} — likely solid-color image. Assigning to noise (cluster_id = NULL).` Do not include in DBSCAN input. |

### Offline Flywheel (Quality Signals Across Runs)

These are not real-time checks — they are signals written to the SQLite metrics table at end-of-run and reviewed by the user when something feels off.

| Metric | What It Signals | Action on Degradation |
|--------|----------------|----------------------|
| **Auto-pick override rate** | `COUNT(*) WHERE cluster_redundant = TRUE AND cluster_keeper != argmax(quality_score)` — fraction of clusters where user overrode the auto-pick | If > 20% of clusters are overridden in a session, the quality weight formula is likely mis-calibrated. Review which component scores are driving wrong picks. Consider retuning sharpness/resolution weights. |
| **Noise rate** | `COUNT(*) WHERE cluster_id IS NULL / total_files` — fraction of files that ended up as noise (no cluster assigned) | If noise rate > 40% for a run that should contain burst sequences, the eps threshold is too tight. Log the k-NN distance distribution for manual review. |
| **Oversized cluster count** | Count of clusters with > 20 photos per run | If > 3 oversized clusters appear in a run, eps may be too loose or a hub image is bridging clusters. Log the file paths of the top-3 largest clusters for inspection. |
| **Skipped (already embedded) rate** | `COUNT(*) WHERE embedding_blob IS NOT NULL / total_files` — fraction of files skipped due to incremental caching | Should be high (> 95%) on incremental runs. If low on an incremental run, the mtime-based cache invalidation may be triggering unnecessarily. |

## 7. Production Monitoring

> Context: "production" for this tool means a CLI run by one user on their own machine. There is no production server, no uptime SLA, and no request/response trace to capture. Monitoring here means: (1) structured per-run metrics written to SQLite so runs are comparable over time, and (2) a Rich end-of-run summary table printed to the terminal so the user can see at a glance whether the pipeline behaved correctly.
>
> Arize Phoenix is noted as the GSD framework default for tracing but is not used here. It requires running a local server process (`px.launch_app()`) and is designed for LLM trace visualization. For a batch CV/ML CLI tool run by one person, the simpler alternative below requires no extra processes, no network ports, and no dependencies beyond the existing SQLite catalog.

### Tracing Approach: Structured Logging + SQLite Metrics Table

**No additional packages required.** Use Python's `logging` module for per-run log files and a dedicated `cluster_runs` table in the catalog SQLite database for cross-run metrics.

**SQLite metrics table schema** (add via migration alongside the Phase 3 column additions):

```sql
CREATE TABLE IF NOT EXISTS cluster_runs (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    run_at          TEXT NOT NULL,          -- ISO-8601 timestamp
    eps             REAL NOT NULL,          -- DBSCAN eps used
    phash_threshold INTEGER NOT NULL,       -- pHash Hamming threshold used
    total_files     INTEGER NOT NULL,       -- total files in catalog at run time
    embedded_files  INTEGER NOT NULL,       -- files with embedding_blob NOT NULL
    newly_embedded  INTEGER NOT NULL,       -- files embedded in this run (incremental delta)
    skipped_cached  INTEGER NOT NULL,       -- files skipped (embedding already present)
    n_clusters      INTEGER NOT NULL,       -- DBSCAN clusters produced
    n_noise         INTEGER NOT NULL,       -- files assigned cluster_id = NULL
    max_cluster_size INTEGER NOT NULL,      -- size of largest cluster
    p90_cluster_size INTEGER NOT NULL,      -- 90th percentile cluster size
    oversized_clusters INTEGER NOT NULL,   -- clusters with > 50 photos
    quality_elapsed_s REAL,                -- wall time for quality scoring pass
    embed_elapsed_s   REAL,                -- wall time for embedding pass
    cluster_elapsed_s REAL,                -- wall time for DBSCAN pass
    total_elapsed_s   REAL NOT NULL        -- total wall time
);
```

**Writing a run record** (in `_run_cluster()` before returning):

```python
import sqlite3
from datetime import datetime, timezone

def _write_run_metrics(catalog_path: str, metrics: dict) -> None:
    con = sqlite3.connect(catalog_path)
    con.execute(
        """
        INSERT INTO cluster_runs (
            run_at, eps, phash_threshold, total_files, embedded_files,
            newly_embedded, skipped_cached, n_clusters, n_noise,
            max_cluster_size, p90_cluster_size, oversized_clusters,
            quality_elapsed_s, embed_elapsed_s, cluster_elapsed_s, total_elapsed_s
        ) VALUES (
            :run_at, :eps, :phash_threshold, :total_files, :embedded_files,
            :newly_embedded, :skipped_cached, :n_clusters, :n_noise,
            :max_cluster_size, :p90_cluster_size, :oversized_clusters,
            :quality_elapsed_s, :embed_elapsed_s, :cluster_elapsed_s, :total_elapsed_s
        )
        """,
        {**metrics, "run_at": datetime.now(timezone.utc).isoformat()},
    )
    con.commit()
    con.close()
```

### Key Metrics to Track Per Run

| Metric | What to Watch |
|--------|--------------|
| `n_clusters` | Should grow gradually with new photo imports. A sudden spike suggests eps is too loose (over-merging stopped — now under-merging and fragmenting). |
| `noise_rate` = `n_noise / total_files` | Normal range: 20–50% (many unique photos have no near-neighbors). If > 70%, eps may be too tight or burst shot detection is broken. |
| `max_cluster_size` | Should stay < 50. If > 100, a hub image is bridging clusters or eps is too high. |
| `skipped_cached` rate = `skipped_cached / embedded_files` | Should be > 90% on incremental runs. If low, cache invalidation is over-triggering. |
| `embed_elapsed_s / newly_embedded` | Per-file embedding time. Baseline: ~80ms/file on CPU. If it exceeds 200ms/file, something has changed (different device, model loaded twice, etc.). |

### Alert Thresholds (User-Visible Warnings in Terminal)

These are printed as Rich `[yellow]WARNING[/]` lines in the summary when thresholds are crossed. No automated alerting — the user reads them.

| Condition | Warning Message |
|-----------|----------------|
| `max_cluster_size > 50` | "Largest cluster has {N} photos — exceeds the 50-photo review limit. Consider lowering `cluster.eps` in config.yaml (try 0.20)." |
| `noise_rate > 0.70` | "More than 70% of files have no cluster assignment. If your library contains many burst shots, `cluster.eps` may be too tight. Try 0.30." |
| `oversized_clusters > 3` | "{N} clusters contain more than 50 photos. Review the largest clusters for hub images (solid-color backgrounds, uniform lighting)." |
| `embed_elapsed_s / newly_embedded > 0.20` | "Embedding is slower than expected ({ms:.0f}ms/file vs. ~80ms baseline). Ensure CLIP model is loaded once, not per-batch." |
| `skipped_cached / embedded_files < 0.80` | "Cache hit rate is low ({rate:.0%}) — more files were re-embedded than expected. Check if mtime-based cache invalidation is triggering incorrectly." |

### Smart Sampling Strategy (Human Review Targeting)

Since the user is the only reviewer, "smart sampling" means directing their attention to the most likely problem areas first when reviewing cluster output.

Prioritize manual inspection for:
1. **Clusters with `max_cluster_size > 20`** — most likely to contain cross-event merges or hub image bridging. Review these first.
2. **Clusters where the auto-pick has `blur_score < 50`** — the keeper may be blurry, suggesting the score formula is over-weighting resolution or EXIF at the expense of sharpness.
3. **Clusters where the top-2 candidates have quality scores within 5 points of each other** — the auto-pick is not decisive; visual comparison is more important here.
4. **Any file path flagged `review_flag = "oversized"` or `review_flag = "zero_embedding"`** — these triggered safety gates and warrant a look.

These filters can be applied at review time:

```bash
# Show only clusters that need attention (oversized or indecisive auto-pick)
photoconsole review-clusters --filter attention
```
